# M0 技术验证：操作说明

目标：用真实账号回答 [方案 §8](../proposal.zh-CN.md) 里的 6 个问题。代码在 [packages/core](../packages/core)，命令行工具是 `gpudock-m0`。

| # | 问题 | 怎么回答 | 花费 |
|---|---|---|---|
| ① | `colaboratory` scope 属于哪一类 | 第 1 步在 Cloud Console 里看，再用 `note` 记下来 | 免费 |
| ② | 账号实际能拿到哪些 GPU | `capacity` | 每个 GPU 几分钟 |
| ③ | 令牌约 1 小时过期后，WebSocket 是否还能用 | `token-expiry` | T4 约 80 分钟 |
| ④ | 空闲多久被回收；持续执行能跑多久 | `idle`、`long-exec` | 最多 4 小时 / 13 小时（可选） |
| ⑤ | 传输吞吐和端到端流程 | `e2e` | T4 约 10 分钟 |
| ⑥ | A100 80GB、H100 的规格字符串和可申请情况 | 用 Pro/Pro+ 账号跑一次 `probe` | 免费 |

## 登录是怎么设计的

普通用户只需要做一件事：运行 `login`（GUI 里就是"用 Google 登录"按钮），在弹出的浏览器里选账号、点"允许"。

这是因为 GPUDock 发布版**自带项目自己的 OAuth 客户端**，和 Google 官方 VS Code 扩展、gcloud 的做法一样。下面第 1 步的 Cloud Console 配置是**维护者只做一次**的事，做完后：

- 你自己的开发机：运行一次 `setup-client`，以后登录不带参数；
- 发布版：CI 在构建时用 `scripts/embed_oauth_client.py` 把客户端打进安装包，用户完全看不到这一步；
- 想用自己客户端的高级用户：仍可用 `login --client-secrets` 或 `--adc`。

## 第 1 步（仅维护者，一次性，约 10 分钟）：创建项目的 OAuth 客户端

1. 打开 <https://console.cloud.google.com/>，新建一个项目，例如 `gpudock`。**这个项目会成为 GPUDock 的"官方客户端"所在项目**，建议用你打算长期维护项目的账号。
2. **启用 Colab API**：打开 <https://console.cloud.google.com/apis/library/colaboratory.googleapis.com>，确认顶部选中了刚建的项目，然后点"启用"。
3. **配置 OAuth 同意屏幕**（Google Auth Platform）：
   - 品牌（Branding）：应用名填 `GPUDock`，填上支持邮箱。
   - 受众（Audience）：用户类型选"外部（External）"。M0 阶段先保持"测试（Testing）"，在"测试用户"里**加上你自己的 Gmail**（最多可加 100 个，邀请早期用户也是在这里加）。
   - **数据访问（Data access）→ 添加或移除范围**：在"手动添加范围"里粘贴
     `https://www.googleapis.com/auth/colaboratory`，点"添加到表格"并保存。
   - 🔍 **问题 ①**：保存后，看这个范围出现在哪一栏："非敏感范围 / 敏感范围 / 受限范围"。**它决定了公开发布前要不要过 Google 审核**，见下表。
4. **创建客户端**：客户端（Clients）→ 创建客户端 → 应用类型选"**桌面应用（Desktop app）**" → 创建 → **下载 JSON**。
5. 安装到本机（只做一次）：

```bash
cd packages/core && uv run gpudock-m0 setup-client ~/Downloads/client_secret_刚下载的文件名.json
```

问题 ① 的结果决定公开发布的路线：

| 分类 | 对最终用户的影响 | 公开发布前要做的事 |
|---|---|---|
| 非敏感 | 无警告、无人数上限 | 把受众从"测试"切到"正式（In production）"即可 |
| 敏感 | 审核通过前会显示"此应用未经验证"，且新用户总数有上限（约 100） | 提交 OAuth 验证：项目主页、隐私政策（都可以放在 GitHub Pages）、已验证的域名、演示视频；通常需要几天到几周 |
| 受限 | 同上，而且审核更严格 | 除验证外还需要每年做第三方安全评估，成本高。届时优先考虑方案里的"浏览器桥接"免配置模式 |

说明：

- "测试"状态下 refresh token 7 天后失效，到时重新 `login` 即可。
- 你用自己的客户端登录时，Google 可能提示"此应用未经验证"，因为它还没过审。这是你自己的应用，点"继续"就行。

## 第 2 步：登录

```bash
cd packages/core && uv sync
```

```bash
uv run gpudock-m0 login
```

浏览器会打开 Google 授权页。选账号、点"允许"后，令牌存进 macOS 钥匙串。检查授权范围是否包含 `colaboratory`：

```bash
uv run gpudock-m0 whoami
```

**网络提示（中国大陆）**：命令行会自动使用 `HTTPS_PROXY` / `HTTP_PROXY` 环境变量里的代理。如果授权完成后浏览器卡在 `localhost:xxxxx` 页面，说明浏览器代理把 localhost 也转发出去了，需要在代理软件里让 `localhost` / `127.0.0.1` 直连。

## 第 3 步：按顺序跑实验

所有结果都追加到当前目录的 `m0-results/results.jsonl`，令牌、运行时完整 URL 和邮箱会被自动去除，可以直接分享。

### 3.1 只读探测（免费）

```bash
uv run gpudock-m0 probe
```

```bash
uv run gpudock-m0 note scope_classification 敏感范围
```

（把"敏感范围"换成你在第 1 步看到的实际分类。）

### 3.2 端到端（⑤，T4 约 10 分钟）

```bash
uv run gpudock-m0 e2e --gpu T4 --size-mb 64
```

依次验证：创建运行时 → Jupyter 状态 → 执行代码 → 机器信息（nvidia-smi）→ 64MB 分片上传 → 运行时内校验 sha256 → 下载并校验 → 中断长任务 → 释放。

### 3.3 能拿到哪些 GPU（②）

```bash
uv run gpudock-m0 capacity --gpus T4,L4,A100,G4
```

每种 GPU 都是"创建 → 读取 nvidia-smi → 立即释放"。不可申请的规格会直接跳过，不会创建。建议在不同时段（工作日白天、晚上）各跑一次，因为容量会随时间变化。

### 3.4 令牌过期（③，T4 约 80 分钟）

```bash
uv run gpudock-m0 token-expiry --gpu T4 --minutes 80
```

运行时会每 30 秒输出一次心跳，同时：

- 用**旧令牌**每 5 分钟调一次 REST，记录它从什么时候开始失效；
- 观察已建立的 WebSocket 在令牌过期后会不会断；
- 如果断了，就刷新令牌、用同一个会话重连，再看心跳是否恢复、断开期间的输出是否补发。

### 3.5 可选：空闲回收与最长执行（④，较贵）

```bash
uv run gpudock-m0 idle --gpu T4 --max-minutes 240
```

```bash
uv run gpudock-m0 long-exec --gpu T4 --hours 13
```

`idle` 期间只查询 Colab API，不碰运行时本身，所以查询不会被算作"活动"。这两个实验耗时长，可以挂在后台跑，或者先跳过。

### 3.6 如有 Pro/Pro+ 账号（⑥）

登录那个账号后再跑一次 `probe`，看 `A100 (HIGHMEM)`、`H100` 是否可申请。

## 第 4 步：生成报告

```bash
uv run gpudock-m0 report
```

生成 `m0-results/REPORT.md`，把它发回来，据此确定 M1 的认证路线和运行时策略。

## 安全与清理

- 每个实验都会在结束时释放自己创建的运行时（`--keep` 除外）。
- 如果中途 Ctrl+C 或网络断开，运行下面的命令。它**只会删除本工具创建的运行时**，你在 Colab 网页里自己开的运行时不会动。

```bash
uv run gpudock-m0 cleanup
```

- 退出登录：`uv run gpudock-m0 logout`。若要彻底撤销授权，到 <https://myaccount.google.com/permissions> 移除该应用。

## 离线自测（不需要 Google 账号）

```bash
uv run pytest -q
```

测试用本地真实的 `jupyter_server` 冒充运行时，覆盖：会话创建、执行和输出、错误、中断、断线重连并补收输出、分片上传、断点续传下载、实验编排，以及"cleanup 不碰用户自己的运行时"。Colab API 部分用 HTTP mock 覆盖了长操作等待、错误原因解析和限流重试。
